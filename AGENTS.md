# Agent Guide: GCS Proxy Development

## Overview

This guide helps AI agents understand the GCS Proxy codebase, common
development tasks, troubleshooting patterns, and key architectural decisions.
Use this as a reference when working on the project.

**gcs-proxy** is a single Go binary that serves HTTP GET and HEAD requests
from the objects of one Google Cloud Storage bucket, with byte ranges and
conditional requests, so that video plays in Safari and on iOS. It passes the
object metadata (`Cache-Control`, `Content-Type`, `ETag`, `Last-Modified`)
through from GCS, maps GCS errors to the matching HTTP status with a generic
message, and is published as a binary and as a container image.

It is a twin of [s3-proxy](https://github.com/dex4er/s3-proxy), started as a
copy of it at commit 08e41b1 and adapted to GCS. The HTTP-facing behaviour,
the build, the release and the CI are kept the same on purpose, so a change
to one project usually applies to the other.

- **`main.go`** — Single entry point; all application logic
- **`main_test.go`** — Unit tests against a fake GCS server
- **`emulator_test.go`** — Integration test against fake-gcs-server, skipped
  without `GCSPROXY_TEST_ENDPOINT`
- **`go.mod`** / **`go.sum`** — Go module dependencies
- **`Makefile`** / **`Makefile.ps1`** — Build and development targets
- **`.goreleaser.yaml`** — Release build configuration (binaries, SBOMs,
  container images)
- **`Dockerfile-goreleaser`** — Container image used by GoReleaser
- **`.trunk/`** — Trunk.io linter/formatter configuration

`GOOGLE_APPLICATION_CREDENTIALS` or `GCSPROXY_*` settings usually live there.

## Build System

### Prerequisites

On macOS and Linux, use [mise](https://mise.jdx.dev/) to manage tools:

```sh
mise install
```

This installs the Go version specified in `.go-version` and the tools
specified in `mise.toml` (goreleaser, yq), verified against `mise.lock`.

A shell that does not activate mise (an agent's non-interactive shell, for
example) gets whatever Go and goreleaser are global, and nothing warns about
the mismatch. Run the tools through mise there:

```sh
mise exec -- go version
mise exec -- make build
```

### Commands

```bash
make download          # Download Go modules
make build             # Build binary for current platform (via goreleaser)
make test              # Run tests
make install           # Build and install binary to $PATH
make tidy              # Tidy Go modules
make upgrade           # Upgrade Go modules
make clean             # Remove built binary and dist/
```

### Build Details

The build uses [goreleaser](https://goreleaser.com/) (configured in
`.goreleaser.yaml`) which produces a statically-linked binary (`CGO_ENABLED=0`)
targeting `amd64` and `arm64` on `darwin`, `linux`, and `windows`.

A release also publishes, per binary, a split `.sha256` checksum and an SPDX
SBOM (`<binary>.sbom.json`, generated by syft), and the release workflow
attests build provenance for the binaries and the SBOMs. Container images for
`linux/amd64` and `linux/arm64` go to Docker Hub and Amazon ECR Public, as
for s3-proxy.

The version is injected by goreleaser's default ldflags (`-X main.version`)
and shown by `gcs-proxy --version`.

To reproduce what a release builds, without publishing:

```bash
goreleaser release --snapshot --clean --skip=publish
```

This needs `syft` on `PATH` for the SBOMs and a running Docker for the
images; add `docker` to `--skip` without one.

The container images need no emulation for either platform: the only `RUN`
in `Dockerfile-goreleaser` is in a stage pinned to `$BUILDPLATFORM`, and the
final stage is `scratch` with `COPY` alone. Keep it that way, or the release
job needs QEMU again.

### Tool Versions

- **Go** is pinned in `.go-version`, which mise, Renovate, `go.mod` and the
  Trunk `go`/`gofmt` entries all follow. `go.mod` is disabled as a mise
  version source in `mise.toml`; see the comment there.
- **goreleaser** and **yq** are pinned in `mise.toml`.
- **`mise.lock`** holds checksums for 8 platforms (linux/macos/windows,
  x64/arm64, plus linux musl). Regenerate it with all of them, or a local
  `mise lock` silently drops the platforms you are not on:

  ```bash
  mise lock --platform linux-arm64,linux-arm64-musl,linux-x64,linux-x64-musl,macos-arm64,macos-x64,windows-arm64,windows-x64
  ```

  Once the file has all platforms, a plain `mise lock` relocks every one of
  them, which is what Renovate's lock file maintenance relies on.

### Clean Build

When facing caching issues:

```bash
make clean
make download
make build
```

## Common Development Tasks

### Configuration

Flags are defined with Cobra and bound to Viper, which also reads environment
variables with the `GCSPROXY_` prefix:

| Flag               | Environment variable      | Default                          | Purpose                                      |
|--------------------|---------------------------|----------------------------------|----------------------------------------------|
| `--bucket`         | `GCSPROXY_BUCKET`         | (required)                       | GCS bucket name                              |
| `--port`           | `GCSPROXY_PORT`           | `8080`                           | HTTP listen port                             |
| `--loglevel`       | `GCSPROXY_LOGLEVEL`       | `info`                           | `debug`, `info`, `warn`, `error`             |
| `--endpoint`       | `GCSPROXY_ENDPOINT`       | `https://storage.googleapis.com` | GCS XML API endpoint URL                     |
| `--anonymous`      | `GCSPROXY_ANONYMOUS`      | `false`                          | Requests without credentials                 |
| `--index-document` | `GCSPROXY_INDEX_DOCUMENT` | (none)                           | Object for a path ending in a slash          |
| `--spa`            | `GCSPROXY_SPA`            | `false`                          | Root index document for dotless paths        |
| `--error-document` | `GCSPROXY_ERROR_DOCUMENT` | (none)                           | Object served with `404` for a missing one   |

A flag name with a dash maps to an underscore in the environment variable
through the key replacer in `initConfig()`, so `--index-document` is
`GCSPROXY_INDEX_DOCUMENT`.

Read configuration through `viper.Get*` in `runServer()`, not through the
flag variables: a value set only in the environment does not reach the flag
variable, and the required-bucket check depends on that (see commit 1fb57ad
in s3-proxy).

Credentials come from Application Default Credentials
(`golang.org/x/oauth2/google`, with the `devstorage.read_only` scope), and
are loaded once at start: a missing ADC fails the start, not the first
request. `--anonymous` skips them, for public buckets and emulators.

The s3-proxy flags with no GCS counterpart are gone: `--region` (the XML
API has one global endpoint) and `--path-style` (the proxy always uses
path-style, see "XML API" below).

### Adding a Flag

1. Register it on `rootCmd.PersistentFlags()` in `init()`
2. Bind it with `viper.BindPFlag` (the env variable follows automatically)
3. Read it with `viper.Get*` in `runServer()`
4. Document it in the README table and in the table above

### Changing Error Mapping

`gcsRequest()` turns every GCS response outside 2xx into a `*gcsError`,
which carries the status, the headers and the `Code` and `Message` of the XML
error body, when there is one. `handleGCSError()` maps it to an HTTP status
by the code where there is one and by the status otherwise. Keep the response
bodies generic: the details go to the log, never to the client.

HEAD responses have no body, so a HEAD error has a status and no code, and
fake-gcs-server answers errors in plain text, not XML. A mapping keyed on
codes alone answers both with `500`; add a case to `TestErrorMapping` for
every code or status you map.

### Running Tests

```bash
make test
```

This runs the unit tests in `main_test.go`, which point the proxy at
`fakeGCS`, an `httptest.Server` that records the requests it gets. Most
cases answer with `http.ServeContent`, which handles ranges and conditional
headers as GCS does. `TestEmulator` in `emulator_test.go` runs the proxy
against a GCS emulator and is skipped unless `GCSPROXY_TEST_ENDPOINT` is
set. The Test workflow runs it against fake-gcs-server; locally:

```bash
docker run -d --rm --name fake-gcs-server -p 4443:4443 \
  fsouza/fake-gcs-server:1.56.1 -scheme http -backend memory -public-host localhost:4443
curl -X POST -H "Content-Type: application/json" -d '{"name":"test-bucket"}' \
  "http://localhost:4443/storage/v1/b?project=test"
GCSPROXY_TEST_ENDPOINT=http://localhost:4443 mise exec -- go test -v ./...
```

What fake-gcs-server (1.56.1) does and does not do, as measured:

- It serves XML API reads, path-style, with `Range`, `416` with
  `Content-Range: bytes */<size>`, HEAD and `404`.
- It **ignores the conditional headers**: no `304` and no `412`. The test
  probes for that and skips the conditional cases, which the unit tests
  cover instead; they run against an emulator that does evaluate them.
- It does not accept XML API uploads (`PUT` answers `invalid uploadType`),
  so the test uploads through the JSON API, and the CI step creates the
  bucket through it too.
- It serves XML API reads only for the host given by `-public-host`
  (`storage.googleapis.com` by default) and answers `404` for any other, so
  `-public-host` has to match the host and port of the test endpoint.
- It serves HTTPS with a self-signed certificate by default, hence
  `-scheme http`. A GitHub Actions service container cannot pass flags,
  which is why the Test workflow starts it from a step.

## Troubleshooting Patterns

### Build Failures

1. Check Go version matches `.go-version`: `mise exec -- go version`
2. Verify modules are downloaded: `go mod download`
3. Check for syntax errors: `go vet ./...`
4. Verify goreleaser config: `goreleaser check`
5. Clean and rebuild: `make clean && make build`

### Runtime Errors

1. `bucket name is required` — neither `--bucket` nor `GCSPROXY_BUCKET` is set
2. `failed to load Google credentials` — no Application Default Credentials
   (`gcloud auth application-default print-access-token` with the same
   environment shows why), or use `--anonymous` for a public bucket
3. Every request returns 403 — the credentials lack `storage.objects.get` on
   the bucket (`roles/storage.objectViewer`); GCS answers 401 for credentials
   it refuses, which the proxy reports as 403 too
4. Video does not play in Safari or on iOS — check that
   `curl -r 0-1 -D - -o /dev/null <url>` answers `206` with a `Content-Range`,
   and that the object has a video `Content-Type` in GCS: one uploaded as
   `application/octet-stream` does not play even with working ranges. An
   object stored with `Content-Encoding: gzip` gets `200` for every range,
   see "Compressed Objects" below

### Linting Errors

Run Trunk to check all linters:

```bash
trunk check
```

For auto-fixing:

```bash
trunk fmt
```

## Architecture Decisions

### Single Binary

The entire proxy is a single Go binary with no external runtime dependencies.
This simplifies distribution and deployment.

### Statically Linked

`CGO_ENABLED=0` ensures the binary has no C library dependencies, making it
portable across Linux distributions and macOS versions, and lets the
container image be `FROM scratch` with only CA certificates added.

### Generic Error Messages

Clients get the original HTTP status but a fixed message, so bucket names,
keys and GCS error details are not leaked. The GCS error code and message are
logged instead.

### Index and Error Documents

These replace the CloudFront Lambda@Edge functions that rewrite SPA routes
to `index.html`, with deliberately simpler rules, all in `indexObject()`:

- `--index-document` appends the document to a path ending in a slash, `/`
  included, the way `MainPageSuffix` of a GCS website does. A path without
  the slash is not tried as a directory: that would cost a second request
  for every missing object.
- `--spa` serves the root index document for every path whose last segment
  has no dot, and leaves the rest alone. There is no exception for an
  assets prefix: a missing `/assets/x.js` is a 404 anyway, because it has a
  dot.
- The rewrite is internal, not a redirect, and happens before anything else,
  so ranges, conditional requests and HEAD work on the index document as on
  any object.

`--error-document` is fetched only for a missing object (`NoSuchKey`, or a
`404` without a code, as HEAD and fake-gcs-server answer), never for a
missing bucket or a denied request, and never for itself, so a missing error
document falls back to the generic `404` instead of looping. It goes to GCS
without the client's `Range` and conditional headers, which were meant for
the missing object, and only its `Content-Type` and `Content-Length` reach
the client: its `ETag`, `Last-Modified` and `Cache-Control` describe the
document, and passing them on would let a client cache the `404` for as long
as the document, or revalidate it against the wrong object.

### Health Endpoint

`/health` returns `200 OK` without touching GCS, so a liveness probe does not
depend on GCS availability or credentials.

### GET and HEAD Only

Any other method returns `405` with `Allow: GET, HEAD`. The proxy is
read-only by design, and asks for the `devstorage.read_only` scope only. HEAD
goes to GCS as HEAD, not as a GET whose body is thrown away.

### XML API

The proxy talks to the GCS XML API with plain `net/http`, not through the
`cloud.google.com/go/storage` client, which uses the JSON API or gRPC:

- The XML API evaluates `Range` and the `If-Match`, `If-None-Match`,
  `If-Modified-Since` and `If-Unmodified-Since` headers itself, and answers
  with `206`, `304`, `412` and `416`, `ETag` and `Last-Modified`, the way S3
  does. That keeps the request handling of s3-proxy nearly unchanged. The
  Go client takes generation preconditions only, so the proxy would have to
  evaluate the HTTP conditions itself and make up an `ETag`.
- The dependencies are `golang.org/x/oauth2` and the metadata client, not
  gRPC and OpenTelemetry.

Requests are path-style, `<endpoint>/<bucket>/<object>`, which works for
every bucket name, dotted names included, over one TLS host name. The object
name is percent-encoded segment by segment in `objectURL()`: slashes stay
path separators, and everything outside the unreserved characters is
encoded, `+` and spaces included, so that no layer reads `+` as a space.

Everything outside 2xx is an error to the proxy, `304` included: GCS errors
carry the validators the `304` must pass on in their headers, which is why
`gcsError` keeps them.

### Compressed Objects

`gcsRequest()` always sends `Accept-Encoding: identity`, for two reasons:

- Without an explicit `Accept-Encoding`, Go's transport asks for gzip and
  decompresses the response on its own, dropping `Content-Length` and
  `Content-Encoding`, so the proxy would not see the response GCS sent.
- An object stored with `Content-Encoding: gzip` would be sent compressed to
  a client that might not accept it. With identity, GCS decompresses it
  itself (decompressive transcoding).

The price is that such an object always gets the whole, decompressed body
with `200`: GCS ignores `Range` while transcoding. Passing the client's
`Accept-Encoding` through, with `Content-Encoding` and `Vary` back, would
keep ranges and compression for those objects; it is not done yet.

### Byte Ranges and Conditional Requests

Safari and AVPlayer start video playback with `Range: bytes=0-1` and do not
play a response that is not `206`, so a proxy without ranges breaks video
while images keep working. Most of the work is left to GCS:

- A single byte range and the `If-Match`, `If-None-Match`,
  `If-Modified-Since` and `If-Unmodified-Since` headers are passed to GCS,
  which answers `206`, `304` or `412`. As RFC 9110 requires, a date
  condition is dropped when its ETag counterpart is present, and a date that
  does not parse is dropped too; a valid one is sent in the preferred
  HTTP-date format.
- A multi-range request or a `Range` that does not parse is dropped, and the
  client gets the whole object with `200`. GCS serves one range per request,
  and RFC 9110 allows ignoring a `Range`.
- **GCS has no `If-Range`**, so the proxy evaluates it: the ranged response
  is fetched first and its `ETag` / `Last-Modified` compared with
  `If-Range`; on a mismatch the body is discarded and the whole object
  fetched instead. Comparing the response rather than asking first keeps the
  common case to one request and leaves no window for the object to change
  in between.
- A range past the end is `416 InvalidRange` to GCS. The `416` has to carry
  the object size in `Content-Range`, so the proxy asks for it with a HEAD,
  and serves the whole object instead when `If-Range` does not match.
  fake-gcs-server puts `Content-Range` and the validators on its `416`, but
  the GCS documentation does not promise that, so the proxy does not rely
  on it.

## Best Practices

1. **Run validation before committing:** `trunk check`
2. **Keep `go.mod` tidy:** run `make tidy` after dependency changes
3. **Run `make test`**, and test against a real GCS bucket before submitting PRs
4. **Follow existing patterns** — the codebase is intentionally minimal
5. **Use `gofmt`** for formatting (enforced by Trunk)
6. **Do not use Anthropic Fable for coding tasks** — Fable may be used only
   for planning, analysis, and thinking through problems. When writing or
   editing code, use standard editing tools instead.

## Conventions

- Do **not** use Conventional Commits prefixes (e.g. `fix:`, `feat:`,
  `chore:`, `refactor:`, `docs:`, `test:`, `ci:`). This project prefers
  plain, descriptive commit messages and PR titles without any prefix.
- Do **not** use emoji in any Markdown, comments, commit messages, or PR
  descriptions. The only exception is emoji that already appears inside code
  strings (e.g. application logs, user-facing messages).
- **One commit per fix** — when a review surfaces more than one issue or the
  plan includes more than one fix, apply and commit each fix separately. This
  keeps the history bisectable and makes each change easy to revert.
